### Do the twelve specs assert what BUILD's table says?

Green is not the same question as correct, so the twelve were audited against the "Key assertions"
column. Ten assert at or above their row. Spec 04 avoided the trap that mattered most: "damage pops
match pipeline numbers" compares the actual numbers against §4.3/§4.4, then cross-checks them against
durable stats. No `cy.get` standing in for an assertion and no `should` without an `expect` was found
anywhere in the suite.

**Spec 09 was the exception, and it is a real defect.** Its row reads *"each of L1–L6 shows its
message; a card dragged into a second deck is refused"*. The spec asserted both against
`PUT /api/loadout` JSON; **no drag occurred anywhere in the suite**, and "shows" was never tested.
The header justified this by saying the deckbuilder vocabulary did not exist — which was stale in
both directions: `e2e/support/testids.ts` exports the full set, `Deckbuilder.tsx` renders all of it,
the two string builders agree byte for byte, and `cy.dragCardToDeck` has been sitting in
`commands.ts:757` as a complete gesture, called by no spec.

Spec 09 now drags. `cy.dragCardToDeck` puts a card already in deck 1 onto deck 2's region and the
refusal is asserted **on screen**: deck 2 never gains the row, deck 1 never loses it, both counts
stay at 20, the pool card carries `data-refused="true"`, and `LOADOUT_ERRORS` still reports
`data-count="0"` — because the refusal is what *kept* the draft legal, which is the difference
between refusing a drag and reporting L4 after the fact.

It carries its own control, and needs one: "refused" and "the gesture never fired" leave an
identical board, so every assertion above would also pass against a `dragCardToDeck` that did
nothing. The same command then drags a card the loadout does not hold onto the same region; it
lands, deck 2 becomes 21, and the builder renders L2's sentence. The gesture demonstrably works and
the refusal is specific to the card being held elsewhere.

**The finding underneath is about BUILD's wording, not the spec.** Only **L2 of the six** is
reachable from a browser at all:

| Rule | Why a browser cannot provoke it |
| --- | --- |
| L1 | The builder always renders three decks; a wrong count cannot be typed in. |
| L3 duplicate, L4 | `addCard` (`deckbuilder/loadout.ts:73`) refuses any card already held in **any** deck. That refusal *is* BUILD's second clause. |
| L3 Token, L6 | `poolFrom` excludes Token-tagged cards and anything the collection does not hold, so neither is ever draggable. |
| L5 | Cannot be isolated under R111, for the reason the spec's header already gave. |

So "each of L1–L6 shows its message" is satisfiable in a browser for one rule. L2's rendered
sentence is asserted twice against the exact validator string — once as the client's live verdict
and once as the server's after a refused save, which is §9.3's two verdicts shown agreeing word for
word. The other five are rendered-message-tested in `Deckbuilder.test.tsx`, the only layer that can
hand the builder an arbitrary draft, each against `validateLoadout`'s own output and each with an
anti-vacuity guard asserting the scenario really breaks the rule it names. Verified independently
for this report.

No product bug surfaced, which is worth stating: a test pointed at the wrong layer for this long
usually hides one.

Three softer spots are recorded rather than fixed, with reasons:

- **Spec 07, "AI actions animate"** — `:310` asserts that *something* on the page carries
  `data-animating`, which the still-draining `attackCancelled` animation from `:301` can satisfy on
  its own. Nothing isolates an AI *play* or *attack* animating. The spec's header concedes this.
- **Spec 10, "code screen shown"** — proved as a URL redirect and an API read; the screen's contents
  are never asserted. Unlike spec 09 this blocker is **genuine**: `invite-code-input`,
  `invite-submit` and `invite-error` really are absent from both the client and `testids.ts`. The
  security-relevant half — the identical error for three failure kinds — is proved thoroughly at the

- **Spec 11, "stats swap keeping damage"** — the health half is proved precisely (a 7/7 body reading
  6/7 with state damage 1, same instance, buffs untouched); the attack half (3 → 7) is never read off
  the card, because `expectShownHealth` reads health only.

## Not verified

- **A GitHub Actions run.** There is no remote. The `checks` job has been executed locally in a
  container via `act`; the `e2e` and `sql` jobs have not been executed in any container, only
  planned, with each of their steps verified individually by hand.
- **Chrome's presence on `ubuntu-latest`.** The matrix assumes the runner image ships Google Chrome.
  The `electron` leg is self-contained (Cypress ships Electron), so a missing Chrome would fail one
  leg loudly rather than pass silently.
- **Real pixel layout at 1280×720 and 390×844.** jsdom cannot measure it and no Cypress spec asserts
  it. The M5-T1 item is therefore a CSS-declaration ceiling check, not a rendered-overflow check.
- **Postgres behind the M6 vitest suites.** Every server test runs against an in-memory fake. T2's
  "one transaction" and T3's unique index are proved there against a re-implementation of the
  database's behaviour; the real ones are proved by the SQL job, separately.
- **The real `viewFor` under the match actor.** M6-T4's leak test runs against a fake engine, so it
  proves the actor and protocol add no leakage *on top of* `viewFor`. The redaction itself is covered
  by `packages/engine/test/viewFor.test.ts`. Nothing wires the real engine into the actor under test.
- **Wall-clock timing of the invite gate.** M6-T1's 5 ms test measures a virtual clock, so it proves
  the padding logic and cannot see a leak from CPU work not routed through `timers.charge`.
- **SQL files 02 and 03** still report failures with `raise notice`, caught only by the runner's
  output grep — a weaker net than 01's `raise exception`. And CHECK 4 has no vacuity guard, because
  `public` holds no functions at all: it is a regression trap, not a measurement.
- **How the `e2e` and `sql` jobs behave on a runner.** Neither has been executed in a container.
  Every step of both was verified individually by hand, and three defects in the `e2e` job were
  found and fixed that way, but the jobs themselves have run only as plans.
- **That the workflow as it now stands is the one that was executed.** It has changed three times
  since the `checks` job last ran green in a container — the Node pin, the readiness probe, and the
  new `sql` job. The `checks` job's steps are untouched by all three, but this is an honest gap
  rather than a verified equivalence.
