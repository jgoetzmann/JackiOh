2. **Extending the `destroyed` payload instead of adding an event type** — **correct, and spec-sanctioned.** R89 names exactly those fields; §10.3's "A new event type is added here and to BUILD M5-T4 together" constrains new *types*, not payloads. The union matches §10.3's list exactly: 40 types in SPEC, 40 in `shared/src/events.ts`, zero in either direction only (diffed mechanically). No finding.
3. **`settle` gaining a `dispatchCursor` on the sink** — **the cause of B-2 and B-3, both BLOCKERs.** The idea (settle mid-action for R62's window without double-dispatching) is sound and its intended half works (`turn.test.ts:362`), but the mechanism drops events in two reachable ways, and the cursors belong in state, not on a transient sink, precisely because a prompt can pause the loop (§9.3).
4. **Echo repeats in `state.echoQueue`, drained by the resolution loop** — **correct, and not a deviation at all**: §6.1 says verbatim "The repeats outstanding live in `state.echoQueue` and resolve one at a time in the resolution loop, so a prompt inside one repeat pauses the rest until it is answered", and §10.1 lists the field. Serializability is tested (`echo.test.ts:187`). The separate ordering bug is B-4.

### B4 — does `rulings.test.ts` satisfy BUILD's M3 gate wording?

**Yes, and I would keep it.** Plainly: BUILD's gate reads "`engine/test/rulings.test.ts` exists with one `it("R<n> …")` per §11 row (R1–R89)". The file generates literally that — one `it` per row read out of SPEC.md at runtime — so the wording is met on its face; the gate then also asserts the ids are contiguous from R1 and that no test names a ruling SPEC does not have. BUILD already contemplates delegation ("rows that only concern cards may delegate to the card test and reference it by name in a comment"); this generalises it from a comment to an automated index, which is strictly stronger — deleting either the SPEC row or the substantive test turns the file red. What it does *not* do is prove anything about a ruling itself: every per-row `it` asserts only `hits.length > 0`. That is fine because the substance is in tests with the same naming convention, but it means the gate's greenness is not evidence a ruling works, and the row-count floor of 84 (B-10) is looser than it should be.

**Coverage is complete**: all 89 rows R1–R89 have at least one `it("R<n> …")` somewhere in the suite (89 distinct ids from a grep over `packages/engine/test/*.test.ts`). Distribution: 42 in `rulings-b`, 40 in `rulings-a`, and the rest spread over 38 behaviour and subsystem files.

**Sampled 21 rows for substance** (across all three files plus behaviour tests). **None is hollow, and none asserts something the engine does not do.**
